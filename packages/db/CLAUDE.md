# @bibi/db – context for Claude

Prisma 7 (the `prisma-client` generator, driver adapter `@prisma/adapter-pg`) against Postgres 17 with pgvector.

## Structure
- `prisma.config.ts` – schema folder, migrations, `DATABASE_URL` (reads the repo root `.env` if present; `generate` works without a database).
- `prisma/schema/*.prisma` – one concept per file: `base.prisma` (generator, datasource, `RecordStatus`), `venue.prisma`, `audit.prisma`, `embedding.prisma`, `conversation.prisma` (Conversation, Message), `skill.prisma`. Better Auth tables go in their own file (`auth.prisma`) via the Better Auth CLI.
- `src/generated/` – generated client (gitignored, `pnpm db:generate`).
- `src/scoped/` – `scopedDb` (tenant protection). `src/embeddings/` – raw SQL for the search index.

## Rules
- Only `packages/core` and `packages/auth` import `@bibi/db` at runtime; elsewhere only types, or a file listed with its reason in `DB_IMPORT_EXEMPTIONS` (`tools/lib/import-rules.mjs`, `check:structure`). Why: ADR 0113.
- Business code **always** uses `scopedDb({ organizationId })`, never `getDb()`/`createDb()` directly.
  - Forces `organizationId` on all reads/writes (where, create, upsert) and removes attempts to change it.
  - Hides `status = ARCHIVED` on reads/updates unless you filter on `status` yourself.
  - Models not listed in `ORG_SCOPED_MODELS` (`src/scoped/models.ts`) are rejected (fail closed). New org model → add it there. Every model is either there or in `UNSCOPED_MODELS` (`GLOBAL_MODELS` + `PLATFORM_MODELS` + `USER_SCOPED_MODELS`); `test/conventions.test.ts` enforces it.
  - `USER_SCOPED_MODELS` (`UserPreference`, ADR 0039; `UserSettings`, ADR 0046; `UserProfile` and `UserWorkingHours`, ADR 0061; `UserWorkingHours` is no longer read since #449 and is dropped in a later release): no `organizationId`; `scopedDb` pins them to the acting user instead (`userId = actorId` on every where/create/upsert, `userId` stripped from updates) and refuses the system actor (`src/scoped/apply-user-scope.ts`, `test/user-scope.test.ts`).
  - Requires `actorId` and forces `createdBy = actorId` on every create of a model in `CREATED_BY_MODELS` (`src/scoped/conventions.ts`); updates cannot change `createdBy`. Handlers never set it. System work uses `SYSTEM_ACTOR_ID`.
  - `SOFT_DELETE_DEFAULTS` controls the default `status` filter per model (Skill: `not ARCHIVED`, others `ACTIVE`).
  - `GLOBAL_READ_MODELS` (Skill): reads see org rows **plus** global rows (`organizationId` null = SYSTEM skills) via an `AND: [{ OR: [{ organizationId }, { organizationId: null }] }]` on top of the caller's `where`. Writes remain locked to the org, so SYSTEM rows can never be created/changed/deleted via `scopedDb` (only via the dedicated seeder in core with `getDb()`).
  - Per-user rules (private conversations, personal skills) live in core, not in the client: `scopedDb` only knows the organization.
  - Record access (ADR 0113): a query on a model in `RECORD_SCOPED_MODELS` (model → root), or a relation hop into one from another root, must declare its intent through `withRecordIntent` (core's `context.records` or `context.engine({ purpose })`); the plain client refuses it. A records query gets the caller's filter at the top level and on list relations (`include`, `select`, named `_count`, `some`/`every`/`none`); a single related record of another root and a blanket `_count: true` are refused. `applyRecordScope` reads and strips the intent (`RECORD_INTENT_KEY`) first. Relations come from `relation-map.generated.ts`: run `pnpm --filter @bibi/db gen:relations` after a schema change (`test/relation-map.test.ts` fails when it is stale).
  - The global `User` row is refused; read the acting user's own name and email with `$callerUser()` (null for SYSTEM and API keys), never `getDb().user`.
  - `AuditLog` and `Message` are append-only. `$queryRaw`/`$executeRaw` are hidden; search/index goes via `$searchEmbeddings`, `$upsertEmbedding`, `$deleteEmbedding`.
  - Relations within an org are also enforced in the database with a composite FK (`Item(venueId, organizationId) → Venue(id, organizationId)`). Do the same for new relations.
  - `BoardPhaseStatus` is a join row (`@@unique([boardId, statusId])`): replace a status's phase by delete and create, never by id list or JSON (ADR 0056, 0067).
  - Writes: use scalar FK fields (`venueId`), not `connect`, because `organizationId` is set as a scalar field.
  - Nested `include` does not filter out archived children – filter explicitly.
  - Hard deletes of a soft-deleted model (`SOFT_DELETE_MODELS`) are refused unless declared through `withHardDelete({ client })` (`src/scoped/hard-delete-intent.ts`, key `$hardDelete`, stripped by `applyScope`). Only core's `archive/` and the kinds' `remove` use it; archiving stays the delete everywhere else. Why: ADR 0118.
- Exception from `scopedDb`: platform code (core `platform/`, ADR 0015) and its tables `SystemLog` and `AiSetting` (`platform.prisma`). They are not org-scoped and `scopedDb` refuses them. `PLATFORM_SCOPE` (`__platform__`) is `AuditLog.organizationId` for platform commands and reserved in `scopedDb`.
- `createSystemLogSink({ retentionDays })` is the logger's sink into `SystemLog`: batches, has a buffer limit and purges old rows every hour.
- Conventions per model: `id String @id @default(cuid(2))`, `organizationId`, `status RecordStatus`, `createdAt`, `updatedAt`, `createdBy`. Exceptions are listed in `src/scoped/conventions.ts` (`COLUMN_EXCEPTIONS`, `APP_ID_MODELS`) and `src/scoped/hard-delete-models.ts` (`HARD_DELETE_MODELS`) and in ADR 0006; `pnpm --filter @bibi/db test` fails for an unlisted violation.
- Skill invariants in the migration `ai_data_layer` (hand-written SQL, Prisma's differ does not touch them): CHECK that SYSTEM ⇔ org null/owner null, ORGANIZATION ⇔ org set/owner null, PERSONAL ⇔ both set; slug format; partial unique indexes for slug per scope among non-archived rows and for `source` among SYSTEM.
- The search index for global entities has `organizationId = GLOBAL_EMBEDDING_SCOPE` (`__global__`); `searchEmbeddings` includes them in every org. `scopedDb` refuses that id.
- Migrations: `pnpm --filter @bibi/db migrate:dev --name <name>`; review the SQL. The vector index (HNSW) is partial (`WHERE embedding IS NOT NULL`) so that Prisma's differ ignores it; `search` is a generated tsvector column (`simple` config, sv+en).
- Expand/contract (ADR 0013): production runs `prisma migrate deploy` (`migrate` service in `docker-compose.prod.yml`) before new containers take traffic, and the previous release keeps running against the new schema during rollout and rollback. Every migration must therefore be backward compatible. Expand: add nullable columns, new tables or indexes, and write both old and new shape. Contract: drop or rename columns, add NOT NULL, or tighten constraints only in a later release, after no running code uses the old shape. Never rename or drop in the same release that stops using it.
- Pool (ADR 0097): each process (web, MCP, worker) opens one `pg` pool of `DATABASE_POOL_MAX` connections (default 10), plus the notification `LISTEN` connection. Keep the sum below Postgres `max_connections`; production sits behind PgBouncer in transaction mode. A page that needs a larger pool needs fewer queries (a view read model, cached loaders), not more connections.
- `process.env` is never read here – use `getEnv()` from `@bibi/config`.

## Database triggers (projections, ADR 0053)
- Triggers are invisible to Prisma and `check:structure`, so they are listed here. SQL lives one file per function under `sql/` and is applied verbatim by a migration (`test/line-holds-sql.test.ts`); each table with a trigger says so in its Prisma doc comment. Application code never writes what a trigger writes.
- `sync_line_occupancy.sql`: line holds (`Occupancy` `HOLD`/`SETUP`/`TEARDOWN` with `lineId`, one row per line, item and type; buffers carry the hold's kind, ADR 0059) and allocation holds (each filled `LineAllocation` of a held line holds its unit for the demand's windows with the line's kind, `allocationId` set; `line_occupancy_wanted` derives both). Triggers on `Line` (insert; update of item, setup, buffer minutes, time, state, order, status), `ItemState` (`hold`, `released`), `Setup` (`changeoverMinutes`), `Item` (`setupMinutes`, `teardownMinutes`), `EntityType` (`capabilities`, `setupMinutes`, `teardownMinutes`; also lines with allocated units of the type), `Order` (`statusId`, `status`), `OrderStatus` (`closes`), `LineAllocation` (insert with a unit; update of unit, status, line, demand) and `ItemDemand` (`windows`, `status`). Configuration changes re-derive only lines that have not ended. An overlap raises `line_occupancy_conflict`, mapped to `CONFLICT` with `lines.<id>` issues. Checked by the `line-holds` reconciliation; only `features/occupancy/write-operations.ts` (manual blocks) and `features/task/sync-task-holds.ts` (task holds, below) write `occupancy` in core (`test/line-holds-writers.test.ts`), and an item's delete removes its rows (ADR 0118).
- Task holds (ADR 0120) are not a trigger: `Occupancy` `HOLD` rows with `taskItemId` (one per `TaskItem` and type, `SOFT` for `PREBOOK`, `HARD` for `BOOK`, the room's own window, no buffers) are a projection written only by core's `syncTaskHolds({ context, taskId })`, called by every task command that changes rooms, done state or status. Active while the task is `ACTIVE` with `doneAt` null; a `CHECK` keeps `lineId` and `taskItemId` exclusive. Checked by the `task-holds` reconciliation.
- `domain_history.sql`: the history triggers (ADR 0054). Inserting into `OrderStatusChange` sets `Order.statusId`, inserting into `LineStateChange` sets `Line.stateId`; a stale insert (a concurrent change won) fails with `history_stale`. Guard triggers on `Order` and `Line` refuse any other update of those columns (`history_projection_only`). Every column is owned, derived, a projection or a snapshot (ADR 0051); projections are written only by the database or one named function and have a reconciliation check.
- `sync_record_relations.sql`: `RecordRelation` (ADR 0113), who is related to an order or item: the creator (`Record.createdBy`, never SYSTEM) and every slot's assignee and followers, chosen or by a responsibility's default (ADR 0055; `record_relation_wanted` derives them). Triggers on `Record` (insert of an order or item), `Line` (insert; update of item, status, order), `Item` (`entityTypeId`), `Assignment` (insert; update of assignee, status, responsibility, record), `AssignmentFollower` (insert, update, delete), `Responsibility` (`defaultAssigneeId`, `status`), `ResponsibilityEntityType` and `ResponsibilityDefaultFollower` (insert, update, delete). It is in `TRIGGER_ONLY_MODELS`, so `scopedDb` refuses every write to it. Checked by the `record-relations` reconciliation.
- `sync_user_name.sql`: `user.name` is the projection of `UserProfile.firstName lastName` (ADR 0061). Trigger on `UserProfile` (insert; update of `firstName`, `lastName`). Better Auth still writes `name` at sign-up, before a profile exists; after that no code writes it.
- `notify_notification.sql`: not a projection, a push signal (ADR 0094). On `Notification` insert and update of `readAt` it calls `pg_notify('notification', {organizationId, recipientUserId})`; the web app listens on one connection per process and pushes the unread count over SSE. It writes nothing.
- `notify_inbox.sql`: a push signal like the one above (ADR 0085, 0094). On `InboundMessage` insert and update of `orderId`, `readAt` or `status` it calls `pg_notify('inbox', {organizationId})`; the same stream pushes the open count for the sidebar's inbox badge. It writes nothing.

## Deleting (ADR 0118)
- Only an archived record with its own page is deleted: `<entity>.delete` for task, customer, item, venue, package (`orderTemplate`), price list, type, list, responsibility, run sheet template, skill (never SYSTEM), status, item type group and order; the nightly `archive.purgeExpired` job deletes those archived longer than `OrganizationProfile.archiveRetentionDays` (1 to 180, CHECK). `archivedAt` is owned: set by the archive, cleared by `<entity>.restore`.
- Refused (`CONFLICT`) while another row refers to it, archived or not; the job deletes referrers first (`PURGE_KINDS` order) and retries the rest the next night. `AuditLog` is never touched; money rows are never deleted.
- Per relation, what a delete does (the kinds in `packages/core/src/features/*/deletion-kind.ts` hold the code):
  - Every record (`Record` supertable): its `RecordLink` rows both ways, `Assignment` + `AssignmentFollower`, `Embedding` and `Record` row are deleted; `RecordRelation` cascades.
  - Task: notifications deleted; `NeedsYouDismissal`, its rooms (`TaskItem`) and their holds cascade. Nothing refuses it.
  - Customer: contacts (and their record rows) deleted. Refused by its orders, tasks, own items and price lists.
  - Item: price list rows, revenue accounts, member profile links, its occupancy (manual blocks), hours, floor plans and layouts with their elements, demands (tags cascade), setups, own parts and customisation groups deleted. Refused by lines, allocations as a unit, order version lines, quote/invoice lines (`OrderLine`), package lines and options, task rooms (`TaskItem`), and other items using it as a part, option or demand target.
  - Venue: hours deleted. Refused by items at it.
  - Package: its lines deleted (options cascade). Refused by inbox endpoints offering it.
  - Price list: its rows deleted.
  - Type: revenue accounts, the join rows of responsibilities and run sheet templates (refused while an active one lists it), grid cells, item states with transitions, and its fields deleted. Refused by any record of it, package and order version lines, boards, inbox endpoints, item demands, other types' link fields.
  - List: run sheet template rows deleted (refused while an active template lists it), values deleted. Refused by fields, requirements and demand tags using it.
  - Responsibility: the assignments on its slots are archived (so the relation trigger lets go) and deleted with followers, its type and default follower rows deleted; `RecordRelation.responsibilityId` cascades. Refused by run sheet templates and run sheets.
  - Run sheet template: its type, field and list rows deleted. Refused by run sheets made from it.
  - Status: board places, grid cells, gates and transitions both ways deleted. Refused by orders in it, status history through it and packages starting in it.
  - Item type group: refused while a type is in it.
  - Order: run sheets (recipients cascade) and their notifications, comments with mentions, draft quotes with their `OrderLine` rows, versions (lines cascade), requirements, allocations, lines and alternative groups deleted; inbox messages are detached (`orderId` null); status and estimate history, mail and dismissals cascade. Refused by any payment, deposit, invoice, quote past `DRAFT` (sent or accepted, ADR 0116) or linked task.
- Append-only and trigger-only rows that belong to a deleted parent go by `ON DELETE CASCADE` (migration `archived_at_and_retention`): `OrderStatusChange`, `OrderEstimate`, `InboundEmail` (order), `LineStateChange` (line), `RunSheetRecipient` (run sheet), `RecordRelation` (record, responsibility).
